# ダンジョン遅延の調査（2026-11-25）

対象は Chari Dungeon: ZERO / charidungeon.com。調査時の本番ソースは dae0629。今回の調査では本番の動作・DB設定を変更していない。ローカルの計測コードと調査記録のみ追加した。ブラウザー検証はすべて mute=1。

## 判断

確認できた主要な問題は、マップの広さそのものより、移動を１件ずつ完了待ちする通信構造、移動中に状態の専用受信を止める条件、移動ごとに繰り返すDB処理である。サーバーのCPUだけを増やしても通信待ちの構造は残る。エリア分割は処理量削減には役立つが、この問題を単独では解消しない。

これは報告されたすべてのフリーズの原因を断定するものではない。実プレイヤー２端末で症状が出ている瞬間の通信RTT・描画時間を同時採取していない。ボス強攻撃中・iPhone Safariのメモリ不足を今回のローカル計測で再現したわけでもない。

## 本番の確認

Supabase SQL Editorと直近60分のログを読み取り調査した。個人情報や通信内容は保存していない。

- 新設の online_combat_pulse 集計：1,851回、DB実行平均11.18ms、最大67.28ms。これは通信往復時間を含まない。deferred応答も含むため、有効なAI更新１回の平均とは限らない。
- ログの呼び出し経路に対応する online_world 集計グループ：1,868回、平均96.59ms、最大537.01ms。操作・pollが混在し、移動だけの計測ではない。他の過去バージョンの集計もあるため、全件合算して現在の平均とは扱わなかった。
- アクティブな冒険部屋２件、最大54体、最大snapshotテキスト31,436bytes。毎回のJSON再送と再書き込みの対象になる。
- 調査瞬間の別セッションのアクティブ処理・Lock待ちは０。症状発生中のロックがないことを証明する数字ではない。
- 直近60分のPostgres ERROR 10件：待機４件、移動速度制限２件、占有マス３件、適用時の書式検査１件（前作業で取り消し後に修正済み）。この範囲にstatement timeout/deadlockはなかった。
- 待機エラーの一例は online_world_adventures line56（wait操作の180ms制限）。すべてをネットワーク障害とは解釈しない。移動速度制限による再試行は別途足止めを加える。
- 同じAPIゲートウェイへの認証なしOPTIONS８回は24～98ms（初回を除く24～53ms）。認証済みゲームRPCの遅延ではなく、経路の参考値に限定する。

## 移動の通信構造

src/online/townScene.ts の queueMove は、１件の移動RPCが返ってから次を送る。先行表示は最大３マス。町では残りをwalk_batchでまとめられるが、敵の９マス以内は常に１歩ずつ送信する。

本番と同じSceneキューを使い、１リクエスト350msを人工的に与え、24マスの入力を152ms間隔で発生させた（DB・描画なし）。

| 条件 | RPC数 | 完了時間 | 実効速度 |
|---|---:|---:|---:|
| 町 | 16 | 5.86秒 | 4.10マス/秒 |
| ダンジョン・敵付近 | 24 | 8.60秒 | 2.79マス/秒 |

設定値はどちらも6.58マス/秒。350msは再現用の値であり、ユーザーの実通信を350msと測定したわけではない。通信が遅くなると、描画を軽くしても入力が詰まることをこのテストで確認した。

さらに full poll と combat pulse の両方が moveSending/requestBusy 中は開始されない。移動が続く間は、敵・味方の更新も移動RPCの返信に依存する。前回のリアルタイム化でもこの結合は残っている。サーバー側も常駐タイマーではなく、リクエストが来たときだけ時計を進める。通信間隔が敵の表示更新間隔に影響する。

## DB処理の比較

同一マシンのローカルPGliteで全migrationを適用し、テスト専用アカウントと部屋だけを使用した。関数ラッパーによる計測の上乗せがあり、本番の絶対速度としては使えない。各８回の中央値、ネットワークなし。生データは outputs/dungeon-lag-db-20261125.jsonl。

| 条件 | 中央値 | 返信サイズの例 |
|---|---:|---:|
| 町・移動 | 6.86ms | 4,013bytes |
| ダンジョン・通常移動、敵は遠方 | 26.77ms | 15,273bytes |
| ダンジョン・専用pulse、敵は遠方 | 4.13ms | 11,175bytes |
| ダンジョン・専用pulse、12体を近くに配置 | 10.16ms | 5,890bytes |

８歩のダンジョン移動で online_maze_sync が52回、online_world_coreが96回、online_world_pre_target_turnsが16回呼ばれた。１歩あたりマップ確認約6.5回、基本状態構築12回。対して町は基本状態構築３回/歩。呼び出しが入れ子なので関数のinclusive時間を合算してはいけない。

現状は移動の検証だけでなく、各機能のラッパーを通り、マップ・装備・ソーシャル情報等を組み直す。敵の更新も、敵１体ごとに共有snapshot JSONを複数回更新する。これらを最初に切り離すべきであり、権限・衝突・アイテム規則を単純に省略してよいという意味ではない。

## 描画だけの比較

ローカルの実ゲームSceneを使い、ネットワークを使わず、同じPC・ブラウザーで各16秒計測。render-frame間隔はrequestAnimationFrameの観測で、Phaserの描画完了時間/GPU時間そのものではない。タブサイズ・PC性能に依存する。

| 条件 | frame間隔 p50 | p95 |
|---|---:|---:|
| 町・待機 | 5.4ms | 10.0ms |
| ダンジョン48体・待機 | 5.1ms | 8.6ms |
| ダンジョン48体・往復移動＋120msごとの疑似状態更新 | 5.1ms | 10.0ms |

移動中のScene update CPUはp50 0.2ms / p95 0.5ms、drawPlayersはp50 0.2ms / p95 0.4ms。この範囲ではダンジョン描画だけによる秒単位停止は再現しなかった。全敵を能動的に動かした実戦・ボス演出・iPhoneで同じ結果になるという保証ではない。

## 修正の優先順

1. ダンジョン用の軽い移動・攻撃経路を用意し、入力番号と座標・必要な差分だけを返す。持ち物・メール・フレンド等の取得と分離する。サーバーの検証は維持する。
2. 移動中も敵・味方の状態を受け取れるようにする。移動の予測・入力番号付きACK・古い返信の棄却を一本化して、待機や巻き戻りを防ぐ。未確認移動を無制限に増やす対処にはしない。
3. 古い処理ラッパーとマップ確認・基本状態取得の重複を整理し、１操作につき必要な更新だけ行う。共有JSONの書き込みもまとめる。
4. リアルタイム戦闘の時計を入力リクエストから独立させる。継続的な同期が必要なら、部屋を担当する常駐処理とWebSocket配信を使う設計が適している。
5. その上でエリア別に敵と通信データを絞る。モンハン型のエリア分割はこの段階で有効。

実症状の最終的な割合は、修正前後の２端末テストでRTT、入力からACK、描画p95、ロック待ちを同じ時間帯で照合する必要がある。
